# PMRK-ID · Профиль контрагента — вкладка «Аффилированность» (группа 21)

Пользователь видит взаимосвязи контрагента с другими организациями и может проанализировать его аффилированность с учетом уровня и типа связи, а также доли владения. Это позволяет оценить контрагента не изолированно, а с учетом связанных с ним организаций и потенциальных групповых рисков.

Сервис-владелец: `affiliation-service`. Источник: **СПАРК** (раздел «СПАРК-Аффилированность»: структура собственников, бенефициары, дочерние и аффилированные лица) → событие `pmrk.integration.spark.affiliation.updated`. Методы: `GetOwnershipHierarchy` — цепочка владения с совладельцами от 5 % кумулятивной доли; `OrderCompanyBeneficiariesAndAffiliates` и затем `GetCompanyBeneficiariesAndAffiliates` — бенефициары (`@IsFinal`) и аффилированные лица с типом связи. `GetCompanyStructure` — доли корневого контрагента в дочерних обществах. Второй метод асинхронный: заказ, затем получение результата; в очереди не более 20 заказов на логин. Перезапрос — только при изменении совладельцев или дочерних компаний по мониторингу СПАРК ([05](../05_Интеграции.md), раздел 4.5). Признак «есть карточка в реестре ПМРК» и `uid` связанного лица — сопоставление по ИНН с реестром `counterparty-service`. Экран прототипа: `AffiliationTabView`, `src/pages/CounterpartyProfile.tsx`; диаграмма — `src/shared/ui/AffiliationDiagram.tsx`.

## Логика экрана, которую обслуживает бэкенд

- Поиск по наименованию/ИНН подсвечивает совпадения; переключатель «Диаграмма / Таблица» сохраняет выбранные типы. Чипы строятся по присутствующим в графе типам из справочника, «Все» сбрасывает выбор. Фильтрация — на клиенте.
- Одно лицо имеет несколько `kinds[]` и показывается в каждой соответствующей группе диаграммы; отдельные записи одного лица для каждого типа не создаются.
- «Структура собственников» объединяет владельцев типа 2 и конечных бенефициаров-ФЛ из отдельного `beneficiaries[]`. Далее идут непустые таблицы остальных типов в порядке справочника. Колонки: наименование, ИНН, тип лица, доля владения; в структуре собственников дополнительно роль. Тип 2 второй раз не дублируется.
- Пустой `beneficiaries[]` означает «Конечный бенефициар — физическое лицо не установлен»; отсутствие массива — сведения ещё не получены. Порог из НСИ не заменяет признак `IsFinal` источника.
- Клик по связанному лицу с карточкой открывает «Общие сведения» его профиля; иначе — заявку на карточку с ИНН или именем. Корневой узел открывает «Общие сведения» текущего контрагента.
- AI-резюме риска группы (AI-8) — [Постановки/80](80_AI_контур.md).

## Загрузка графа из СПАРК

Граф — read-модель СПАРК: ПМРК не создаёт и не правит узлы, а заменяет граф при каждой успешной загрузке. Запросы в СПАРК выполняет `integration-hub`; модуль `affiliation` получает готовый список узлов событием `pmrk.integration.spark.affiliation.updated` (состав — [06](../06_События.md), раздел 2.2) и сохраняет его. Элементы XML ниже — по XSD ответов `OwnershipHierarchy.xsd` и `CompanyBeneficiariesAndAffiliates.xsd` (общие типы — `CommonTypes.xsd`), которые публикует тестовый шлюз СПАРК: `http://sparkgatetest.interfax.ru/iFaxWebService/Schemas/<имя>.xsd`. Классы `SparkClient` генерируются из этих схем.

| № | Шаг | Альтернативный сценарий |
|---|---|---|
| 1 | `integration-hub` получает триггер: создание карточки (`pmrk.counterparty.profile.created`), событие мониторинга СПАРК об изменении совладельцев или дочерних компаний, команду `pmrk.integration.spark.refresh.requested` | |
| 2 | В одной сессии вызывает `GetOwnershipHierarchy` и `GetCompanyStructure` по ИНН корневого контрагента и заказывает `OrderCompanyBeneficiariesAndAffiliates`; результат заказа забирает `GetCompanyBeneficiariesAndAffiliates` по `orderId`. При любом триггере вызываются все три метода: событие несёт полный граф | 2а. Очередь заказов логина заполнена — заказ откладывается фоновым заданием |
| 3 | Сопоставляет корневую компанию с контрагентом ПМРК по ИНН | 3а. Не сопоставлена — запись в карантин, граф не меняется |
| 4 | Строит ключ лица для каждой записи обоих ответов (`Coowner`, `Beneficiary`, `Affiliate`): `spark:{SparkID}`, если в записи есть `SparkID`; иначе `inn:{ИНН}`; иначе `name:P:{хэш}` или `name:L:{хэш}` — SHA-256 нормализованного наименования (верхний регистр, без кавычек, организационно-правовой формы и повторных пробелов) с признаком физического (`P`) или юридического (`L`) лица | |
| 5 | Склеивает записи с одинаковым ключом в один узел по таблице маппинга ниже. В `Affiliates` у записи ровно один `AffiliationType`, поэтому лицо с несколькими типами связи приходит несколькими записями — их типы объединяются. Корневой контрагент в узлы не включается | 5а. Конечный бенефициар без иных ролей — узел с пустым `kinds`. 5б. Неизвестный код типа — карантин маппинга с исходным кодом; узел сохраняется с известными типами |
| 6 | Публикует событие с полным списком узлов и датой актуальности источника | |
| 7 | Модуль `affiliation` в одной транзакции фиксирует inbox, заменяет шапку графа и все его узлы, публикует `pmrk.affiliation.links.updated` | 7а. Повтор события с тем же `eventId` — эффект не повторяется. 7б. Версия источника старее сохранённой — событие отклоняется |

Маппинг полей СПАРК → узел (БО 21.2):

| Поле узла | `GetOwnershipHierarchy` · `Report/Coowners/Coowner` | `GetCompanyBeneficiariesAndAffiliates` · `Report/Beneficiaries/Beneficiary`, `Report/Affiliates/Affiliate` | Правило при склейке |
|---|---|---|---|
| `name`, `inn` | `Name`, `INN` | `Name`, `INN` | Первое непустое значение: совладелец, бенефициар, аффилированное лицо |
| `isPerson` | `CoownerType = 2` | `@Type = 2` | Признак ФЛ в любой записи |
| `kinds` | — | `AffiliationType/@Id` | Объединение кодов без повторов, порядок справочника. Подпись типа — по справочнику постановки; `AffiliationType/@Name` источника не выводится (В-26) |
| `level` | `Level` | — | Уровень совладельца; лицо, которого нет среди совладельцев, — `1` |
| `parentIds[]` | `ParentId` (может повторяться) | — | Суррогатные `Id` ответа заменяются на `id` узлов; `Id` между загрузками не хранится |
| `directShare`, `directShareRub`, `indirectShare` | `SharePart`, `SharePartRUR`, `IndirectSharePart` | — | `SharePart = 0` при заполненной `IndirectSharePart` — прямой доли нет. Доли дочерних обществ — строкой ниже |
| `directShare`, `directShareRub` дочернего общества | — | — | Из `GetCompanyStructure` · `Report/AffiliatedCompaniesEGRUL/AffiliatedCompanyEGRUL`, при отсутствии компании там — `AffiliatedCompaniesRosstat/AffiliatedCompanyRosstat`, затем `AffiliatedCompaniesFCSM/AffiliatedCompanyFCSM` (только %): `SharePart`, `SharePartRUR`. Компания сопоставляется с узлом по тому же ключу (`SparkID`, ИНН, наименование) и только с узлом, у которого есть тип 1. Дочерние компании, которых нет среди аффилированных лиц, новых узлов не создают |
| `coownerType`, `manager` | `CoownerType`, `Manager` | — | Только у совладельцев |
| `isFinalBeneficiary`, `notFinalReason` | — | `Beneficiary/@IsFinal`, `NotFinalReason/@Name` | Только у бенефициаров |
| `isDirector` | — | тип 3 в `kinds` | Вычисляется |
| `underSanctions` | — | — | Не из этих методов: при чтении по ИНН в `affiliation.sanctions_ref` (пакет X-Compliance). В проекцию попадают лица с действующей санкцией; списки наблюдения и правило 50 % не учитываются ([05](../05_Интеграции.md), раздел 4.5) |
| дата графа (`updatedAt` БО 21.1) | `ActualDate` | — | Самая поздняя дата среди совладельцев |

Граф заменяется только целиком. Если хотя бы один из трёх методов вернул `Error`, `Access denied` или исчерпал повторы, событие не публикуется, прежний граф сохраняется, ошибка фиксируется в мониторинге интеграций. Ответ `Data not found` означает отсутствие данных этого метода: для `GetOwnershipHierarchy` — нет совладельцев, для `GetCompanyStructure` — доли дочерних обществ не заполняются, для бенефициаров — пустой `beneficiaries[]` («не установлен»).

`id` узла равен ключу лица из шага 4 и не меняется между загрузками, пока источник не изменит идентификацию лица. Узел, исчезнувший из ответа СПАРК, удаляется при замене графа. Суррогатные `Coowner/Id` действуют только внутри одного ответа и в `id` узла не используются.
