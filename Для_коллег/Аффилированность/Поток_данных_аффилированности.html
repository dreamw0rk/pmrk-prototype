Аффилированность: от вызова СПАРК до схемы на экране

Сквозной пример на одном контрагенте: какие методы СПАРК вызываются и что они возвращают, как три ответа склеиваются в один граф, что лежит в таблицах схемы affiliation и что получает фронт в GET /affiliation-graphs/v1/{uid}.

шаг 1ТриггерСоздана карточка, мониторинг СПАРК, «Обновить внешние данные»
шаг 2СПАРК, 3 методаВладельцы, доли в дочерних, бенефициары и типы связи
шаг 3integration-hubСклеивает записи в узлы и отправляет полный граф в ядро
шаг 4Модуль affiliationЗаменяет граф целиком в схеме affiliation
шаг 5ФронтЧитает граф, обогащённый карточками, оценками и санкциями

Данные в примерах — условные: контрагент, ИНН и SparkID придуманы, но имена элементов XML и полей JSON — реальные, по XSD СПАРК и OpenAPI ПМРК. В СПАРК при открытии вкладки никто не ходит: экран читает только локальные таблицы (НФТ-Пр-2).

1. Схема потока

Запросы в СПАРК делает отдельное приложение pmrk-integration (модуль integration-hub). Граф хранит модуль affiliation внутри ядра pmrk-core. Между приложениями события ходят по HTTP через outbox отправителя и inbox получателя, Kafka в первой версии нет.

3. Вызовы СПАРК

СПАРК — SOAP-сервис. Сессия открывается Authmethod и живёт в cookie ASP.NET_SessionId; внутри одной сессии вызовы идут строго последовательно. Каждый метод возвращает статус в …Result и данные строкой XML в xmlData. Классы для разбора генерируются из XSD (JAXB).

  participant IH as integration-hub
  participant SP as СПАРК

  SP-->>IH: True + cookie ASP.NET_SessionId
  IH->>SP: GetOwnershipHierarchy(code = 7801234567)
  SP-->>IH: xmlData — Report/Coowners
  IH->>SP: GetCompanyStructure(inn = 7801234567)
  SP-->>IH: xmlData — Report/AffiliatedCompanies*
  IH->>SP: OrderCompanyBeneficiariesAndAffiliates(inn = 7801234567)

  IH->>SP: GetCompanyBeneficiariesAndAffiliates(orderId = 4471020)
  SP-->>IH: Order is in progress — повторить позже
  IH->>SP: GetCompanyBeneficiariesAndAffiliates(orderId = 4471020)
  SP-->>IH: xmlData — Beneficiaries, Affiliates
  IH->>SP: End()

4. Склейка в узлы integration-hub

Из трёх ответов получается 12 записей о четырёх лицах. integration-hub сводит их в четыре узла. Ключ лица и одновременно id узла строится так:

  1. spark:{SparkID}, если в записи есть SparkID;
  2. иначе inn:{ИНН};
  3. иначе name:P:{хэш} для физлица или name:L:{хэш} для юрлица — SHA-256 нормализованного наименования (верхний регистр, без кавычек, без организационно-правовой формы и лишних пробелов).

Такой id не меняется между загрузками. У Смирнова нет SparkID, поэтому его ключ — inn:780512345678, и как бенефициар он получает тот же id.

6. Хранение в БД схема affiliation

Модуль в одной транзакции: фиксирует eventId в inbox (повтор не задвоит данные), проверяет sourceVersion (старое событие отклоняется), удаляет узлы контрагента и пишет новые, обновляет шапку и публикует affiliation.links.updated. Признак «есть карточка», оценка, вердикт и санкции не хранятся в узле — они подставляются при чтении из трёх служебных таблиц.

7. Санкции связанных лиц X-Compliance

Проверять каждого связанного по отдельности дорого: это вызов на лицо. Поэтому integration-hub раз в сутки забирает пакетную выгрузку X-Compliance и передаёт в ядро только ИНН лиц под санкциями. Санкции самого контрагента загружаются по алгоритму ЕДТ (GetCompanySanctionList), этот поток их не касается.

8. Отдача на фронт affiliation → фронт

HTTP
GET /affiliation-graphs/v1/5b0c1d9e-3f6a-4c2b-9d1e-7a8b9c0d1e2f
Authorization: Bearer …

Что делает модуль при чтении. Внешних вызовов нет, только локальные таблицы:

  1. Читает шапку и узлы графа. Графа нет и контрагент неизвестен — 404; контрагент известен, но граф не загружен — пустой nodes.
  2. Для каждого узла с ИНН ищет его в inn_registry → inRegistry, counterpartyUid.
  3. Для найденных карточек берёт оценку из assessment_risk_ref → creditGroup, score.
  4. Проверяет ИНН в sanctions_ref → underSanctions.
  5. Для узлов с карточкой считает вердикт: санкции, банкротство или ликвидация, группа 4 → «Высокий риск»; группа 3 → «С осторожностью»; иначе «Можно работать».
  6. Собирает kinds[] — записи справочника НСИ «Типы аффилированности» только по кодам, которые есть в графе, в порядке справочника.
  7. Делит узлы на nodes[] и beneficiaries[] (по признаку конечного бенефициара; одно лицо может быть в обоих списках с одним id), подставляет порог бенефициара из НСИ (25).

9. Кто ещё слушает граф limits

После замены графа (и когда у связанного лица появляется или пропадает карточка) модуль affiliation публикует pmrk.affiliation.links.updated. Модуль лимитов держит копию в limits.affiliate_link и пересчитывает «Совокупный КЛ аффилированных лиц» на вкладке «Кредитный лимит». В событие попадают только лица с карточкой в ПМРК.

{
  "counterpartyUid": "5b0c1d9e-3f6a-4c2b-9d1e-7a8b9c0d1e2f",
  "graphVersion": 7,
  "linkedCounterparties": [
    { "counterpartyUid": "8e1f2a3b-4c5d-4e6f-8a9b-0c1d2e3f4a5b", "kinds": [2, 9], "level": 1 },
    { "counterpartyUid": "c2d3e4f5-a6b7-4c8d-9e0f-1a2b3c4d5e6f", "kinds": [1, 8], "level": 1 }

Каких связанных лиц учитывать в сумме КЛ (все типы и уровни или часть) — открытый вопрос заказчику В-29. Типы и уровень передаются, чтобы отбор можно было включить без доработки события.

11. Проверить на первом реальном вызове

Схемы не перечисляют часть значений. Их нужно зафиксировать по первому ответу с логином СПАРК:

  • Направление Coowner/ParentId: у владельца 2-го уровня он указывает на компанию 1-го уровня (так следует из описания «непосредственный совладелец»).
  • Приходит ли SparkID у физлиц-совладельцев и бенефициаров; без него ключ — ИНН.
  • Значения параметра type у GetCompanyComplianceData и GetPersonComplianceData: какое даёт полный массив, какое — изменения за сутки.
  • Код типа ИНН в reg_data/item/@type (юрлица) и в persdocs/item (name, tag) у физлиц.
  • Формат архива пакетной выгрузки: один XML или несколько, кодировка.
